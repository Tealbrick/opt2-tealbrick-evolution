# Evolving Workflows (Tealbrick mini app)

Evolution (product id `evolution`): the mini app that turns work your agents repeat into reviewed, versioned workflows, and exports a recipe that creates a Bound agent for a workflow. Workflows can run on a schedule through that Bound agent. Evolution never starts an agent and never calls a model. Built on the Miniapp SDK.

**Status:** stable 0.2.11; `main` is 0.2.12 (dev channel only; its qa1 soak is the gate for stable, C221). Visibility: public, Apache-2.0. Image: `ghcr.io/tealbrick/opt2-tealbrick-evolution` (publicly pullable; as of 2026-10-17 it holds the tags 0.2.12, its earlier dev pre-release 0.2.12-dev.1, and `sha-` tags; 0.2.11 and older were published under the former owner's GHCR namespace). Step A (0.1): suggestions, owner review, drafts, versions, diffs, recipe export, Task Board pattern detector. Step B (0.2): schedules and runs claimed at most once by the Bound agent's own runner (`tealbrick agent serve` in routines mode); every run is a Task Board issue assigned to the Bound agent. Release B (0.3.0, C250, on `main` before its version chore): the cycle ledger and an eval per cycle (Cycles page), T1 evals in CI (`eval/`).

## What it does

```
agent repeats work ──suggestion_create (evidence: Task Board issue ids / receipt call ids, steps)──┐
Task Board done issues ──detector (same template or title, one agent, N >= 3)──────────────────────┤
                                                                                                   ▼
owner (person ops): review → approve → draft (steps, allowed ops per product, trigger) → promote v1, v2 …
                    → diff versions → recipe_export (tealbrick.recipe/1) → owner imports + applies it in Portal
                    → a Bound agent whose grant allows only the workflow's operations
                    → schedule (cron, UTC) → the agent's runner: routines_due → routine_claim → one turn → routine_report
                    → every run = one Task Board issue assigned to the Bound agent (template evolution:<workflow id>)
```

The UI says it plainly: **the agent may call these operations** (the bridge blocks every other one); the steps are reviewed guidance, not an enforced program. The allow-list is enforced by the bridge. Temporal and the v1 step runner are not part of opt2.

### Schedules and runs (0.2)

- occurrence = sha256 of `[automationId, revision, dueAt]`; the primary key of the run row (`routine_runs`) makes a claim at-most-once (v1 routines model).
- Misfire grace (default 120 s, `cronDue`): a due time not claimed in time is recorded `missed` once, missed periods collapse into that record, and the next period runs; never a burst of catch-up runs.
- `claimed` over 10 minutes or `dispatched` over 30 minutes without a report → `uncertain`, never offered again (a late report still closes it).
- Following the active version: if it allows more than the version whose recipe the owner applied (`policyVersion`), the schedule shows a `policy_stale` warning, `routines_due` does not offer its due run, and its periods are skipped like claimed ones; the first one per schedule revision and version is recorded as a `policy_stale` run (`runs_list`; a claim answers `policy_stale`). After the owner applies the new recipe in Portal and sets "Recipe applied" (`policyVersion`) with Edit on the Schedules page, the next period runs; a period already skipped is not run again (a repeated claim of a skipped period without a row answers `not_due`). An edit that does not name `policyVersion` keeps it. One gate (`policyStale` in `src/routines.ts`) decides this for `routines_due` and `routine_claim` (0.2.13, C250).
- Task Board (companion `issue_create`, `issue_complete`, `issue_block`): one issue per claimed run, assigned to the Bound agent, template `evolution:<workflow id>`; the detector never suggests these. Task Board down → the run still runs (`kanbanSync: failed`).
- Run issue project: the schedule's `kanbanProject`. Use a Task Board project the owner SHARES with the Bound agent, so the agent can read and comment on its run issues (shared projects reach agents and Evolution). When Evolution can reach Task Board (its companion grant is in the workspace slice, `kanbanLinked`), a NEW schedule needs `kanbanProject` (`422 kanban_project_required`); an edit can keep an older schedule without one, never remove one, and such a schedule carries the `kanban_project_missing` warning. Without a project, run issues go to Evolution's own Task Board project, which the Bound agent cannot see (0.2.13, C250). Every recipe allows `kanban.issue_get` and `kanban.issue_comment_add` for this.
- Free target (C364a R1a): `automation_set` takes an optional `targetMode` (`bound`, the default, or `free`; an edit without it keeps the stored mode). A `free` schedule names an existing Free agent from the workspace agent list: that agent claims its runs with its own grant (no narrowing, no wider than its own cron runs today). `422 agent_not_free` when the agent is not listed or not in mode Free; `422 policy_version_not_applicable` when `policyVersion` is sent (no recipe is applied to a Free agent, so the `policy_stale` gate does not apply). `routines_due` and `routine_claim` match on (schedule agent = caller AND schedule `targetMode` = caller mode): a Free agent reaches only its own Free schedules, never another agent's; a Bound caller never gets or claims a Free schedule and the reverse. Claim reasons: `mode_mismatch` (the occurrence is one of the caller's own schedules of the other mode), `not_bound` (not an agent, or a Free agent that has no Free schedule), `agent_unavailable` (the agent is paused or removed). Occurrence, the at-most-once insert, grace, the uncertain sweep and the run issue assigned to the claimer are unchanged. Evolution does not enforce the operation list for a Free claimer (no run token yet): the Schedules page and `workflow_get` (Free caller) say "Runs with <agent>'s own access. The operation list is guidance until per-run narrowing (C288 R2–R4)." `ALLOWLIST_NOTICE` stays for Bound.
- Paused or removed agent: Evolution keeps the agent directory it is told about (`agentAdded`, `agentsChanged`, `agentRemoved`; mode, status and whether the agent is still listed, in `agent_names`). A paused or removed agent is offered no job and cannot claim, in both modes. The SDK refuses such a caller before the handler runs (`agent_paused`, `agent_unknown`); the handler asks the directory again as a second layer. An agent Evolution has no row for passes the handler check (the SDK admits only slice agents).
- Cron and the due / misfire rule: `nextCronTime` and `cronDue` from `@opt2-tealbrick/manifest` (5 fields, UTC; the one shared helper, no local copy). `routines_due` only books what the clock and the policy gate imply (`missed`, `policy_stale`); it never claims. Nothing starts runs on a timer; the runner is external.

### Cycles and evals (0.3.0, C250 Release B)

- A cycle is one workflow version, from its promotion until the next version of the same workflow is promoted (`retiredAt`; null = active). The ledger is computed on read from `workflow_versions`, `drafts`, `suggestions` and `routine_runs` (`src/cycles.ts`); nothing is copied. Owner only (person ops), no Task Board evidence titles, no cost fields (E2 later). `workflowTitle` is the workflow's title, which may come from a detector suggestion built from a Task Board title (C88): it is owner-only, like `workflows_list`.
- Per cycle: authoring (`parentVersion`, `suggestionId`, `evidenceCount`, `approvalDelayMs` = the FIRST approval event minus the suggestion's creation (a later archive does not change it), `draftRevisions`, `widensAccess` against the parent) and runs (`counts` total / completed / failed / uncertain / missed / policyStale / open, `completedRatio`, `uncertainRatio`, `failedRatio`, `missedRatio`, `claimLatencyP50Ms`, `durationP50Ms`, `kanbanClosedRatio`, `duplicateClaims`, `last10`). A run belongs to its `workflow_version`; a 0.2.x `missed` row without one belongs to the version active at its due time. From 0.3.0 a `missed` row stores its version (the pin, else the version active at the due time). Stale `claimed` / `dispatched` runs count as uncertain (the `runs_list` rule). Ratios use completed + failed + uncertain as the base (`missedRatio` adds missed); medians are nearest-rank (lower middle). `durationP50Ms` = `reported_at` minus `claimed_at` of completed / failed runs: `reported_at` (0.3.0, migration 0005) is set by the runner's terminal `routine_report`, never by the sweep, so a later Task Board close (which moves `updated_at`) does not count. Rows from before 0.3.0 have no `reported_at` and are left out.
- Eval (`src/evals.ts`, one `tealbrick.eval/1` result per metric, suite `cycle:<workflow id>@v<n>`, tier T2). Gates: `duplicate_claims` = 0, `uncertain_ratio` <= 0.05, `completed_ratio` >= 0.80, `completed_ratio_drop` (parent minus this) <= 0.10. Information: `missed_ratio` <= 0.20, `policy_stale_runs`. A ratio needs 5 terminal runs (the drop: 5 in both cycles), else `pass: null`. Verdict: `fail` if a gate fails, `pass` if every gate passes, else `insufficient`. Version 1 has no parent, so no drop metric. Thresholds: `eval/thresholds.json` (the one source).
- Stored evals (`eval_runs`, migration 0005): promoting version n+1 stores the closing eval of version n in the same transaction (trigger `promotion`), best effort: a nested transaction (savepoint), so a failing eval is logged (ids, the error message and a store code; no Task Board data) and rolled back alone and never fails the promotion; "Store eval now" on the Cycles page calls `cycle_eval_run` (trigger `owner`). The live eval of every cycle is computed on read.

### Run metrics (C288 R8)

- `routine_report` takes an OPTIONAL `metrics` object, the `RunReport` of the Henry contracts: `ok` (boolean, required), `minutes` (number 0..10080, required), `retries` and `questions_to_martin` (whole numbers 0..1000), `lessons` (at most 20 strings, each 1..280 characters counted as code points, stored trimmed, and each must show at least one letter, digit, punctuation or symbol: zero-width and filler characters alone are blank; the schema counts the raw length). Also `metrics`: the named per-pipeline numbers (RunReport.metrics, agent-stack 640a4aa): an object of name to number, at most 20 names, each name `^[a-z][a-z0-9_]{1,40}$`, finite numbers from -1e12 to 1e12 (a pointer names the bad name: `/metrics/metrics/<name>`; the bound keeps every sum and mean finite). A workflow VERSION keeps at most 20 DISTINCT names over all its runs (the cycle ledger lists them): a report that would add a 21st name is refused `422 metric_names_full` with the pointer of that name, and the usual retry rule applies (send the report again without metrics, or only the names the version already has). Which names are allowed: when the workflow version was imported from a pipeline contract, only the names it declares (`metric_not_declared`, see "Pipeline contract (C288 R10)"); a version that was not imported accepts any patterned name. No other field. `pipeline` (string, at most 64), `version` (whole number, at least 1) and `issue` (the Task Board issue id of the run, string 1..64) are accepted for 1:1 compatibility with `RunReport` and are IGNORED: Henry's pipeline ids and contract version are not our workflow id and version, and the run row is the truth for both, and the run row's own `kanban_issue_id` is the truth for the issue. They are never stored or compared. **Bounds differ from Henry's schema on purpose** (Henry's `RunReport` has no length limits on `pipeline` and `issue`, no range on `version`, and no value range on named metrics): Evolution bounds `pipeline` and `issue` to 64 characters, `version` to 1..100000 and named values to |v| <= 1e12. Henry's runtime keeps ids short, so a Henry-style report fits; a report outside the bounds is refused by the schema and the runner retries without metrics. A report without `metrics` works exactly as before (old runners keep working).
- Metrics are accepted only with the report that moves the run to `completed` or `failed` (a late report of a run the sweep made `uncertain` counts). On any other status: `422 metrics_need_terminal_status`. They are stored in the same transaction as the status change, once. A REPEAT of the current status is a no-op, as for every report: metrics that arrive on it (same or different) are not stored and never overwrite the stored ones; a run that finished without metrics stays without. A bad payload is still refused on a repeat. **If a report with metrics is refused, send the same report again without metrics, so the run still ends** (a refused report changes nothing). The answer to the agent is the run, as before: no op for agents returns metrics or lessons.
- Invalid shapes are refused by the manifest schema before the handler: the SDK answers `400 input_invalid` with the JSON pointer of each error (`/metrics/minutes`, `/metrics/lessons/2`, ...), as for every op. The handler repeats the bounds (`422 validation_failed` with a pointer; the lesson blank check is in the schema pattern too) so a direct call cannot store a value outside them. `ok` is not checked against the status: it is the runner's own word (a completed run can say `ok: false`).
- Stored in the new table `run_metrics` (migration 0006, one row per run, keyed by the occurrence); the named numbers go to the child table `run_metric_values` (occurrence, name, value; the same migration file, with CHECKs on the name, a finite value and at most 20 names per run). 0006 was extended in place, before any release (R8 is PR #14, no tag): no database has applied the first form. The run row stays the truth for the workflow and version. The rollup `runMetrics` of every cycle (`cycles_list`, `cycle_get`, the Cycles page): `runs` (with metrics), `okRuns`, `okRatio`, `minutesMedian` (nearest-rank, lower middle), `minutesMean`, `retriesTotal`, `questionsToMartinTotal` (a run that left a field out counts 0), `lessonCount`, and `namedMetrics`: one entry per name (sorted) with `reports`, `median` (nearest-rank, lower middle), `mean`, `min` and `max`, over the runs of that version that reported the name. The Cycles page lists them by name (underscores read as spaces) and compares the typical (median) value of a name with the previous version once BOTH versions have at least 5 reports of THAT name ("candidates seen: typical 12 → 15"); a name with fewer says "too few reports to compare yet". Two versions of one workflow are compared through `parentVersion`; the Timeline on the Cycles page says how the share reported as done well and the typical (median) time moved against the previous version, once BOTH versions have at least 5 run reports with metrics (the floor of the evals); before that it says "Too few reports to compare yet". There is no eval gate on these numbers.
- C88 / L12: `lessons` are free text from agents. Only the owner reads them: `cycle_get` (person op, newest first, at most 500; `runMetrics.lessonCount` is the full count) and "Show lessons" on the Cycles page (plain text, never markup). `test/run-metrics.test.ts` proves that no agent op returns metrics or lessons.

### Pipeline contract (C288 R10)

Martin: workflow definitions import or map 1:1 the typed pipeline contract. The contract is `tealbrick.agents/pipeline-contract/0.1` (the Henry typed contracts). Its JSON Schema is vendored in `contracts/pipeline-contract-0.1.schema.json` (provenance in its `$comment`; the test pins a digest of its content). Contracts are checked with `validateAgainstSchema` of `@opt2-tealbrick/manifest` (the SDK's own JSON Schema 2020-12 validator): every keyword of the schema is enforced, there is no hand-written subset. A leading `$schema` text (the example files carry one) is set aside before the check, as the reference validator of the contracts does, and is kept.

**`pipeline_import`** (person, `{contract, asDraftOf?}`, idempotency required, receipt names only the pipeline id) answers `{draft, report}`. The draft is an ordinary open draft the owner edits and promotes as today. It does NOT create a schedule.

| Contract | Becomes |
|---|---|
| `id` | the pipeline key, stored with the draft (the title is the id made readable, for example "P1 daily tidbit") |
| `version` | stored as data (`pipelineVersion`); Evolution versions stay its own |
| `purpose` | the summary |
| `steps[].id`, `steps[].do` | step id (a duplicate id is refused), step instruction (all of `do`) and step title (first line, at most 100 characters) |
| `steps[].tools` named `mcp__tealbrick__<product>__<operation>` | the step operations and the allowed operations (access guessed by `guessCrud`, the owner can change it before promotion) |
| every other tool (local tools, `buzz ...`, `mcp__<other>__...`, `connect ...`, a malformed Teal Brick name) | NOT mapped: listed in `report.unmapped.tools` as `{step, tool, reason}`, once per step and tool. The name rule is the draft editor's (the manifest patterns for `allowed`). Also refused although well formed: product `tb` (standard operations are never in an allow-list), product `evolution` other than the Bound-agent operations (`routine_claim`, `routine_report`, `routines_due`, `workflow_get`), and an operation name with `__`. They are not enforced and not in the allow-list (C288 R5 and R6 are owned by the contracts lead and the Agents lane) |
| `trigger` | trigger text in words only. `report.schedule_hint` gives `{cron, timezone, event, once}` (timezone `Asia/Bangkok` when the contract has a cron and no zone, the schema default) for the owner to create the schedule by hand: Evolution schedules run in UTC and have no zone (V1-PARITY Q5 is open) |
| `metrics` (the names of the per-pipeline numbers; patterned `^[a-z][a-z0-9_]{1,40}$`, unique, at most 20, and never a core RunReport field: pipeline, version, ok, minutes, retries, questions_to_martin, lessons, issue) | `report.declaredMetrics`, in contract order. The runner of the workflow reports them as `routine_report` `metrics.metrics` (name to number). A name the version does not declare is refused (see below) |
| `owner`, `status`, `dictation_refs`, `inputs`, `outputs`, `done_when`, `approvals`, `escalation`, `taskboard`, `steps[].lead`, `skills`, `in`, `out`, `when`, `on_fail` | kept as data, not enforced (`report.kept_as_data`). The typed interpreter of in / out / when / on_fail is C264 |

The whole contract is stored as it came in (`pipeline_sources.source`), so nothing is lost. What an agent that runs the workflow can read of it: the title, summary and steps (`report.agent_visible`; the draft page says so in plain words). The owner reviews and can edit them before promotion. Dictation references, escalation, approvals, inputs, outputs and done checks stay with the owner. Bounds, checked first: the serialized contract is at most 256 KiB and every array in it has at most 200 items, else `422 contract_too_large` with `details.pointer`. The report is also checked against the output schema of `pipeline_import` BEFORE the draft is created (for example more than 600 `mapped` lines): over a cap is `422 contract_too_large` (pointer `/steps` or `/metrics`) and nothing is created. Refusals: an invalid contract is `422 validation_failed` with `details.pointer` (JSON pointer of the first problem, for example `/steps/1/on_fail`; an unknown field is named, `/steps/0/foo`) and `details.errors`; a contract that is valid but maps to a draft beyond the draft limits (a step `do` over 4000 characters, more than 50 steps) is refused the same way, with the pointer in contract terms (`/steps/0/do`). `asDraftOf` makes the draft a new draft of that workflow (promotion makes its next version; the workflow's own title and instruction are kept, the rest comes from the contract). If the workflow already carries another pipeline key, the answer is `409 pipeline_id_mismatch`; a workflow that was never imported accepts any key and takes it, but only with `confirmReplace: true` (else `409 confirm_replace_required`: the draft replaces its steps and allowed operations; the Drafts page asks with a "Replace and import" button). The draft records the version that was active at import (`pipeline.baseVersion`). Importing a key again without `asDraftOf` creates a separate draft and says in the report which workflow already has it.

**`pipeline_export`** (person, `{workflowId, version?}`) answers `{contract, filename, imported, omitted, notice}`: a pipeline contract 0.1 object rebuilt from the version snapshot and the contract frozen with that version. It always validates against the schema (checked before it leaves).

- Imported version: starts from the stored contract, so everything Evolution does not own comes back as it came in. Evolution owns exactly three things: `status` (`active` for the active version, `retired` for an older one; the stored status is not returned), `purpose` (the summary: an edit shows; a value that only differs by surrounding spaces comes back as imported), `steps` (which steps exist, their order, `do` = the step instruction, and the Teal Brick `tools` = the step operations: a removed operation goes, an added one is appended; unmapped tools and `lead / skills / in / out / when / on_fail` stay with the step id they were imported with; a step added in Evolution gets its id made valid and unique, and never one of the ids of the imported contract). An unchanged import round-trips: import, promote, export gives the same object except `status`. The test does this for all 8 example pipelines.
- Not exported, because the contract has no place for them: the draft title, the instruction for the Bound agent, the trigger text, and allowed operations that no step uses (named in `omitted`; the contract lists tools per step).
- A workflow that was never imported (or a version promoted from a draft that was not) gets defaults for the required fields: `id` from the title (or `wfl-<id>`), `version` = the Evolution version number, `owner` `unassigned`, `purpose` = summary (else the title), `trigger` = the cron of its first schedule, or the trigger text when the cron parser of the schedules accepts it, with timezone `UTC` (else `{event: "manual"}`, and the notice says that the text is not in the file), `inputs` = the Task Board run issue, `outputs` and `done_when` = the run issue closed with the result, `approvals` `{}`, `escalation` `[]`, `metrics` = `[]` (the core RunReport names are not allowed in that list), and one step `run` when there are no steps.

Declared metrics (R10 with the named metrics of R8): when the workflow VERSION a run belongs to was imported from a contract, `routine_report` accepts a named metric (`metrics.metrics.<name>`) only if that contract declares it: otherwise `422 metric_not_declared` with `details.pointer` `/metrics/metrics/<name>`. It is refused like the other metrics errors (also on a repeat; the run is unchanged; the documented retry rule applies: send the report again without metrics). The answer does not list the declared names. The run decides the version, so a v2 contract does not change what a v1 run may report. A version that was never imported accepts any patterned name. A version imported with an EMPTY metrics list declares none: every named metric is refused (core fields still pass). I kept it strict because an empty list is the contract saying "nothing to report"; an owner who wants free names imports a contract that declares them, or promotes a version that was not imported. The Cycles page lists the declared names of a version in contract order and says "not reported yet" for a name without data (`declaredMetrics` in `cycles_list` and `cycle_get`).

Where it lives: migration `0007_pipeline_contract.sql` adds two tables and changes nothing else: `pipeline_sources` (per draft: key, version, the contract, the import report) and `workflow_version_pipelines` (the contract frozen with each promoted version, copied by `workflow_promote` in its transaction). It is not part of the version snapshot, so diffs, `workflow_get` and everything an agent reads are unchanged. C88 / L12: the stored contract holds dictation refs, owners and purposes. Only person ops read it (`draft_get` adds `pipeline`, `workflow_versions` adds `pipelines`, `pipeline_export`). No agent op returns it; the purpose is the workflow summary the owner promoted, as for any workflow. Agents are not affected by R10: `skills/use-evolution/SKILL.md` is unchanged. UI: every draft of an existing workflow that allows more than the active version shows the same "allows more than" notice as the Workflows page; a draft imported with `asDraftOf` warns when another version became active after its base ("based on v1; v2 is now active"). Drafts has "Import pipeline contract" (paste JSON, optional "new version of"), the draft shows "Imported from pipeline contract <id> v<n>" and the report in plain words; the Workflows page has "Export pipeline contract" (downloads the JSON).

### Workflow engine (C367, WP2: contract + Temporal interpreter)

`src/engine/` runs typed workflows (`tealbrick.workflow/1`) on a Temporal worker inside this app. Temporal itself is a companion service (WP1); the app reads `TEMPORAL_ADDRESS` (namespace and task queue `evolution`). Without that variable the engine is off and the app behaves as 0.3.x.

- **Contract** (`contract.ts`, `contract-schema.ts`, `validate.ts`): step kinds `app`, `ai`, `approval`, `transform`, `timer`, `condition`, `loop`, `parallel`, `workflow`, an optional `stage` label, refs (`$input`, `$steps.<id>.output`, `$trigger`, `$loop.item`), `{{ }}` templates and a small safe expression set (no code). `validateContract()` refuses unresolved refs, type clashes, unbounded loops, an `app` op that is not an agent op of an installed app (or not in this app's companion list), a write op without idempotency (unless `onFail: "ask"`) and an unknown model role.
- **Interpreter** (`workflow.ts`): one workflow type `evolutionRun({workflowId, version, runId, trigger})`, workflow id `evo:<workflowId>:<runId>`. The definition is loaded by an activity, never embedded in a Schedule. Changes of behaviour use `patched()`; CI replays stored histories (`test/engine/replay.test.ts`).
- **Grants** (ENGINE-BUILD §4, M1): the manifest asks for a SUPERSET companion block (agent ops of Task Board, Knowledge, Inbox, Rules; Connect read ops and `tools`; no delete, send or money op). The owner activates a version (`workflow_activate`) and sees the ops, CRUD and scopes it uses; the engine refuses any other call of that workflow (`not_in_workflow`), and for Connect `tools` any other tool. The bridge limits Evolving Workflows as a whole; each workflow's limit is enforced by the engine until per-workflow grants (P1).
- **Schedules** (`schedules.ts`): Temporal Schedules with cron or interval and an IANA time zone, overlap SKIP, catch-up window 1 h, pause, run now, update, delete. A `poll` schedule stops early when the cursor did not change.
- **Run index** (`migrations/0009_engine.sql`, `engine-store.ts`, `reconcile.ts`): `engine_runs` / `engine_steps` hold ids, status, timing, attempts, held waits and sizes, never the data of other apps. Temporal wins: a reconcile job on boot and every 10 minutes closes, adds and repairs rows. Cycles read `engine_runs` too.
- **Agent steps**: `agent-port.ts` is the fixed seam to the agent-step runtime (`AgentStepPort`); a role call uses `ModelPort` (M2).
- **Build**: `scripts/build-workflows.ts` bundles the workflow code once (`dist/engine/workflow-bundle.js`); `scripts/sync-target-ops.ts` regenerates `src/engine/target-ops.json` (the SDK cannot read an installed target manifest) and the companion block.
- **Tests**: `test/engine/` uses `@temporalio/testing` (a downloaded test server; CI needs network access to temporal.download).

### Agent steps (engine line, C367 WP3)

An `ai` step of a workflow can name an agent card (`by: {agent}`) instead of a model role. The engine offers the step to that agent, the agent returns a typed output, and the engine runs every action itself. The agent step is content only: the answer of `step_claim` says `mode: "content"` and "Return the output only. Do not act."

- Agent ops (verified caller only): `steps_due` (the caller's offered steps: `stepRunId`, `workflowTitle`, `deadline`), `step_claim` (at most once; the same agent asking again for a step it claimed, because its answer was lost, gets the same payload again as a read that changes nothing; returns `instruction`, `inputs`, `outputSchema`, `allowedHint`, `deadline`, `heartbeatSec`, `mode`, `note`), `step_heartbeat`, `step_report` (`completed` with the `output`, or `failed`; optional `summary` and `metrics`). The runner config for `tealbrick agent serve` is the routines mode config with `routines: [{due: "evolution__steps_due", claim: "evolution__step_claim", report: "evolution__step_report", items: "steps", id: "stepRunId"}]` (copyable on the Runs page); the runner must also call `step_heartbeat` while it works.
- R1a rules, as for schedules: a caller gets and claims a step only when (step agent = caller AND step mode = caller mode). The engine offers to Free agents only (they act with their own grant). A Bound agent, another Free agent, a paused agent and a removed agent get nothing. Claim reasons: `already_claimed`, `finished`, `timed_out`, `cancelled`, `not_found` (not yours looks like not there), `mode_mismatch`, `agent_unavailable`.
- `step_report` checks the output against the `outputSchema` of the step. A wrong output is `422 output_invalid` with a pointer (`/output/bullets`); the step stays claimed until it times out, so the agent can report again. A valid output completes the Temporal activity (`client.activity.complete`); `failed` fails it (`client.activity.fail`) and the step's retry decides whether the engine offers it again as the next attempt.
- Time: `deadline` is Temporal's startToClose; the heartbeat window is 3 x `heartbeatSec` (none when `heartbeatSec` is 0). Temporal decides; `agent_step_runs` mirrors it, and a refused heartbeat (`step_timed_out`, `step_cancelled`) tells the agent to stop. Claiming counts as the first heartbeat.
- Stored in `agent_step_runs` and `agent_step_events` (0010): the offer while the step is open, then only the size and sha256 of the answer, the agent's one-line summary and its numbers. The inputs (they can hold other apps' data) and the task token are removed when the step ends; the output body is never stored. `step_claim` takes no idempotency key, so the SDK keeps no copy of its answer either. Owner op `agent_steps_list` shows the history per attempt (offered, claimed, timed out); it never shows inputs or output.
- Wiring (`wireAgentSteps(db)` in `src/agentsteps/wire.ts`, called from `onStart`): `registerAgentPort(createAgentStepPort(db))` is the port the engine's `ai` activity offers through, and `setCompletionProvider(completionFromTemporal(getTemporal))` gives step_report the engine's Temporal client. While Temporal is down, completing a step answers `503 engine_unavailable`.
- `heartbeatSec` 0 (the contract default) means the workflow asks for no heartbeat: Temporal sets no heartbeat timeout and only the deadline ends the step. A failed report reaches the run as the step error `AgentStepFailed` with the agent's one-line reason.

### Engine pages of the owner UI (C367 WP3)

Editor, Activation and Runs are new pages; Schedules and Cycles gain an engine section.

- **Editor**: a typed step list with a form per step kind (app, ai, transform, approval, timer, condition, loop, parallel, workflow), the six-lane **Shape** view (event, process, enrichment, concat, intelligence, result action; the intelligent lane may be empty), the contract as JSON, and a live check (shape, ids, refs, bounds) with a pointer for each problem. **Save version** calls `workflow_contract_save`: it stores an immutable contract version in the engine at once (no draft, no promote); **Saved versions** lists them (`workflow_contracts_list`) and **Open** loads one (`workflow_contract_get`). A saved version never changes: to change it, raise the contract version and save again. "Check with the engine" calls `workflow_contract_validate` for what needs the installed apps (WP2's `validateContract()` runs on the server, because it needs the apps' catalog).
- **Activation**: picks a saved version (`workflow_contracts_list`; the state is active, superseded or deactivated), lists the operations, the access (CRUD) and the scopes that a version uses, with the honest label "the bridge limits Evolving Workflows as a whole; each workflow's limit is enforced by the engine until per-workflow grants (P1)", then Activate or Deactivate.
- **Schedules**: the engine schedules (cron or interval such as `15m`, IANA time zone, overlap skip or keep one) with Run now ("Run started"; the engine gives no run id, a Temporal Schedule starts the run), Pause, Edit and Delete, below the 0.3.x agent schedules.
- **Runs**: the engine's runs, and for a run the step timeline (statuses as the index stores them: running, completed, failed, skipped, waiting for your approval, waiting for your answer, waiting for an agent): status, attempt and timing of each step, a link to the hold a step waits on, and for an agent step the card that was offered it, who claimed it and where it timed out. Owner only.
- **Cycles**: engine runs next to the legacy runs of each workflow version.
- The ops of the engine are WP2's (`src/engine/ops.ts`); the pages call them through the generated kit types (`src/ui/engine-ops.ts`). `src/ui/engine-contract.ts` re-exports WP2's contract types and limits (`src/engine/contract.ts`, `contract-schema.ts`) and holds the editor's quick check.

### Move from 0.3.x (C367 M3)

One time, when the first version of the engine line starts (`src/migrate/run.ts`, from `onStart`, after the SQL migrations), Evolution moves the 0.3.x agent workflows to the engine. A marker row (`migration_marker`, name `m3_from_0_3`) says it is done; from then on it is a no-op. Until it is done (the engine is off, `TEMPORAL_ADDRESS` not set) it runs again at each start and only does what is not done.

- **Workflows.** Every promoted version becomes a contract version (`engine_definitions`; engine id = the 0.3.x id in lower case with hyphens, same version number): one `ai` step `by: {agent}`. Its `instruction` is the version's instruction, its trigger text and the reviewed steps with their operations. `outputSchema` is `{type: object, properties: {summary: string}, required: [summary]}`, `timeoutSec` 1800 (the 0.3.x limit of a dispatched run), `heartbeatSec` 0 (a 0.3.x runner does not heartbeat). The triggers are a `manual` trigger, plus a `schedule` trigger (cron, UTC) when a schedule moved. The agent is the one of the workflow's first Free schedule. The contract schema needs an agent id, so a workflow with no Free schedule gets the placeholder `agt_unassigned`, is NOT activated, and its summary says to choose the agent in the editor. A version whose instruction and steps are over the engine's 8000 characters is not moved; the reason is in the move summary.
- **Schedules.** A Free schedule becomes an engine schedule (same cron, time zone `UTC`, overlap skip, pinned to its version or else the active one; paused if it was paused). The versions it needs are activated with no operations: an agent step calls no app, so there is nothing to approve. The 0.3.x schedule is PAUSED, never deleted, and its `routine_runs` are never touched: Cycles keeps them as legacy runs, next to the engine runs of the same workflow.
- **Bound agents stay.** Agent steps go to Free agents only, so a schedule with a Bound target is not moved. It keeps working on `routines_due` / `routine_claim` / `routine_report` and carries the warning `legacy_bound` in `automations_list`. (Every 0.3.0 schedule is Bound: on 0.3.0 data the move changes no schedule.) A second Free agent on one workflow stays on the old path too (`skipped`, `other_agent`).
- **Rollback.** Pause or delete the engine schedule, then resume the 0.3.x schedule (the `migrated` warning on it says so). Never run both. The contracts stay; deleting them is not part of a rollback.
- **Compatibility layer, deprecated for one release.** `routines_due`, `routine_claim` and `routine_report` work as before for Bound agents on 0.3.x schedules. For a schedule that moved, `routines_due` offers nothing and `routine_claim` answers `migrated`: the agent takes the work as steps (`steps_due`, `step_claim`, `step_report`). The three `routines_*` ops are removed in the release after this one.
- **Owner UI.** `migration_status` feeds the "Migrated from 0.3" badge (Workflows, engine schedules, Runs) and the summary on the Workflows page: counts moved, kept on 0.3.x (`legacy_bound`), skipped, failed (with the reason) and waiting for the engine.
- **Known limit.** A moved workflow is still an instruction that the agent carries out with its own tools, but every agent step answers "Return the output only. Do not act." The owner decides whether such a workflow stays as it is (the Bound path) or is rewritten as content steps plus engine actions.
- `scripts/upgrade-check.ts` runs the move twice on a copy of a real `app.db`, checks that the second run changes nothing, that no 0.3.x row changes except the pause of a moved schedule, and that every moved schedule is still there, paused.

### T1 evals (`eval/`)

`node eval/run.ts [--out <file>]` runs two synthetic, public-safe suites through the real code and prints one `tealbrick.eval/1` line (JSON) per metric; exit 1 on any failure. CI runs it on every pipeline (`tealbrick-ci.json` `preReleaseChecks`, ci-v9.6+).

- `eval/cases/detector/*.json` (49 Task Board histories, 32 must-suggest groups): `parseDoneIssues` + `buildGroups` + the N filter, as the scan does. ANY case mismatch fails the run. Cases with `knownMiss: true` (3 near-duplicates: word order, plural, typo; pinned in a test) carry the gold group the detector should reach (E5 targets): only missing gold groups are tolerated (reported in the `known_misses` line, kept out of precision and recall); a wrong extra group fails, and a full match fails with "known miss now passes: remove knownMiss", so E5 progress is locked in. Precision and recall over the other cases must reach the measured baseline 1.0 / 1.0 (`thresholds.json`; G6 floors 0.9 / 0.8).
- `eval/cases/cycles/*.json` (20 run histories, incl. exactly 5 terminal runs: the minimum sample is inclusive): `runStats` + `cycleEval` + `verdictOf`; every expected verdict and metric value must match.
- `test/evals.test.ts` proves the runner exits 1 on a mutated threshold, a wrong expected list, one extra or one missing group, and four broken detectors (status filter, covered set, non-agent flat assignee, number normalisation); all in memory, the corpus is never edited to make a test pass.

### Task Board (soft dependency)

The manifest declares one companion product, `kanban`, with four operations: `issues_list` (read), `issue_create`, `issue_complete` and `issue_block`. The detector calls `issues_list` with `{"status": "done", "limit": 200}` and reads `issues[]` with `id`, `title`, `status`, `assignee {kind, id, name}` (only `kind: "agent"` counts) and `template`. Without Task Board the scan answers `unavailable` and Evolution works with agent suggestions alone (run issues are then not created). The scan runs in the background (first scan 60 s after start, then every 15 minutes) as an app-initiated companion call with Evolution's own grant, and on demand (`detector_scan`); `detector_status` shows the last result. What Evolution read with its own grant (Task Board titles and the text built from them) is shown only to the owner; agents see detector suggestions as fixed text plus issue ids. Evolution sees done work only in the projects the owner shares with it (shared projects, or projects granted to Evolution on the Task Board scopes page).

### Recipe

`recipe_export` emits a `tealbrick.recipe/1` (Portal API section 3) with no `ws` and no concrete Portal id (`$ref` to step 0's output). The Bound agent's allowlist always includes `evolution.workflow_get`. Apply it with `tealbrick recipe import <file>` and the review link, then one confirmation in the browser. The default agent harness choice in the UI is "Other agent (MCP)".

## Environment

The SDK reads only `TB_*` variables (SDK API section 13). The Dockerfile defaults `TB_DATA_DIR=/data` (the `data` volume mount) and `TB_BACKUP_DIR=/data/backup` (one volume per service). The deploy recipe sets the rest: `TB_INSTANCE_ID`, `TB_ENROL_CODE`, `TB_BRIDGE_URL`, `TB_PORTAL_KEYS`, `TB_KEK`. Optional: `TB_LOG_LEVEL`, `TB_RESTORE_FROM`, `TB_STANDALONE`. The listen port is the manifest `runtime.port`. The app has no keys. One app-specific variable: `TEMPORAL_ADDRESS` (`host:7233`), set by the deploy recipe from the manifest (`{{services.temporal.host}}:7233`); without it the engine is not probed. `TB_DATA_EPHEMERAL=1` is for tests and local runs only; never set it in a deploy recipe.

## Release

1. Set the same version in `package.json` and `tealbrick.manifest.json`.
2. Tag `v<semver>` on a green pipeline and push the tag. The GitHub Actions workflow builds and publishes the image and kit (release assets only from CI). Tags are immutable.
3. The platform signer indexes the release (`registry-sync` signs the index entry with the image digest and the manifest digest).
4. Core deploys the newest stable version when the owner installs or updates the app. An update that fails keeps the previous version serving.

Check `publisher` and `source.repo` in the manifest. The repository name must match the image name in `tealbrick-ci.json` (`opt2-tealbrick-evolution`).

### Before an update to 0.4

Update these apps first. Core refuses the update, with nothing changed, while one of them is older: bridge 0.2.11, Knowledge 0.1.29, Task Board 0.1.15, Inbox 0.3.0, Rules 0.3.0, Connect 0.6.0. A workspace on 0.2.x goes to 0.3.0 first (`upgradeFrom` is `>=0.3.0 <0.4.1`).

## Dependency pins

`@opt2-tealbrick/*` dependencies are pinned as tarball URLs on the dist host (`Tealbrick/opt2-tealbrick-dist` releases). `pnpm-lock.yaml` carries the sha512 integrity of every such tarball. After changing one, run `pnpm install`, then `node <opt2-tealbrick-platform>/ci/tb-ci.ts pin-tarballs .`, then `pnpm install --frozen-lockfile`, and commit the lockfile. Image builds run `pnpm install --frozen-lockfile --ignore-scripts`.
